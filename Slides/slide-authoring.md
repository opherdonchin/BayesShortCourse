# Slide authoring — Short Bayes Course

These guidelines are for the two-day **Short Practical Introduction to Bayesian Analysis**. They are intentionally lighter than the conventions used for a semester-long course: this repository needs a coherent, readable deck that can be revised quickly and that works together with live notebooks.

## Purpose of the slides

The slides support the spoken lecture and the computational notebooks; they are not a self-contained textbook or handout.

A slide should normally do one main teaching job:

- pose a question;
- introduce a model or assumption;
- show a figure, equation, or result;
- make a comparison;
- summarize a workflow step; or
- mark a transition to or from a notebook.

Prefer a sequence of simple slides over one dense slide that tries to carry the whole explanation.

## Before editing slides

1. Read this file.
2. Read the surrounding slides in `Slides/slide_deck.typ` so the local narrative is clear.
3. When a slide depends on a notebook, inspect the relevant notebook rather than duplicating or guessing what it does.
4. Preserve the timing and role of the live notebook demonstrations. The deck should frame them, not compete with them.

Do not import conventions from another course merely because they exist there. Reuse a pattern only when it serves this short course.

## Tooling and shared template

- Slides are written in Typst with Touying.
- `Slides/course.typ` owns the theme configuration, course metadata, and a very small set of genuinely shared helpers.
- `Slides/slide_deck.typ` should contain the intellectual sequence and slide content, not repeated theme setup.
- Keep the existing Touying version stable while editing lecture content. Treat a Touying/Typst upgrade as a separate change that is compiled and visually checked before adoption.
- The current base theme is Touying Metropolis. Do not replace it without a concrete visual or pedagogical reason.

Keep `course.typ` thin. A helper belongs there when it removes repeated presentation infrastructure or when the same visual pattern is genuinely reused. Do not build a component system in anticipation of needs that have not appeared.

## Slide structure

Use Touying heading levels consistently:

- `= Section title` for major lecture sections;
- `== Slide title` for ordinary slides.

Use the shared title-slide and outline helpers from `course.typ` rather than repeating their implementation in the deck.

Section titles may be simple labels. Ordinary slide titles should, when practical, state the question, claim, contrast, or teaching move rather than merely naming a topic.

Good:

```typst
== Posterior predictive: can the model reproduce the experiment?
```

Less useful:

```typst
== Posterior predictive
```

## Density and visual hierarchy

- Prefer one main idea or object per slide.
- Keep prose short. Slides should be easy to scan from the back of a room.
- Use a small number of short bullets when bullets are the clearest form; avoid paragraph-length bullets.
- Prefer a well-sized figure, equation, or schematic over text describing the same thing.
- Do not shrink text aggressively to rescue an overfull slide. Split the slide instead.
- Use progressive reveals only when the order of appearance is part of the explanation.
- Do not add visual variation merely for novelty.

A summary or workflow slide may be denser than an explanatory slide when the density itself helps the audience see the structure.

## Relationship to notebooks

The notebooks carry computation. The slides carry framing, scientific interpretation, and the structure of the workflow.

- Do not paste substantial code onto slides unless the code syntax itself is the teaching point.
- When demonstrating a notebook live, the preceding slide should make clear what question the audience should watch the notebook answer.
- After a substantial notebook segment, use a slide when useful to state the conclusion, limitation, or next modeling move.
- It is fine for a slide figure to be generated by the same notebook used in the demonstration, but the slide should not become a screenshot of the notebook interface.

## Bayesian workflow conventions

When the lecture presents an analysis, keep the inferential sequence visible. As appropriate to the example:

1. state the scientific question;
2. specify the generative model;
3. make the prior assumptions explicit;
4. inspect prior implications by simulation;
5. fit the model;
6. check sampling diagnostics before substantive interpretation;
7. inspect posterior quantities that answer the scientific question;
8. use posterior predictive simulation/checks to ask what the fitted model predicts;
9. revise the model when a meaningful mismatch appears.

Do not force every example to display every step on its own slide. The point is to preserve the logic of the workflow across the lecture.

Distinguish clearly between:

- uncertainty about parameters or average effects; and
- predictive variation for new observations or individuals.

When a derived quantity is the scientific target (for example LD50), give it visual and narrative priority rather than treating it as an afterthought.

## Equations and notation

- Use equations when they clarify the model, not to signal mathematical seriousness.
- Keep notation consistent across slides and notebooks.
- Show the generative relationship before focusing on posterior summaries when that relationship is important to understanding the example.
- Avoid placing several new symbols, assumptions, and inferential conclusions on the same slide.

## Figures

- Prefer figures generated reproducibly from the course notebooks or small figure-generation scripts.
- Notebook figures are saved to `Slides/figures/` as `<notebook>_<section>[_<n>].svg`; see *Figures for slides* in `AGENTS.md`. Reference them from there rather than redrawing notebook plots in Typst.
- Prefer vector output such as SVG when practical; use high-resolution raster images when vector output is inappropriate.
- Avoid screenshots of plots when the underlying figure can be exported directly.
- Make labels, legends, lines, and annotations large enough for projection.
- External figures should have a concise source citation on the slide or immediately adjacent to the figure.
- Missing figures are acceptable while drafting but not in a lecture-ready deck.

Direct `image(...)` usage is fine. Add a shared figure helper to `course.typ` only if repeated figure formatting makes that worthwhile.

## Speaker notes

Speaker notes are optional in this short course. Add them when they preserve something that is easy to forget while presenting: a transition, caveat, question for the room, interpretation, or reminder about the live demonstration.

Do not require notes on every substantive slide, and do not use notes merely to restate visible text.

## Drafting and review

During drafting, placeholders and TODOs are acceptable.

Before treating the deck as lecture-ready:

- compile the Typst source cleanly;
- check that all referenced assets exist;
- inspect the rendered PDF, not only the source;
- check for overflow, clipping, tiny text, weak contrast, and unreadable figures;
- check the narrative transition across neighboring slides;
- check that the amount of slide material is realistic given the planned notebook demonstrations and discussion time.

Compilation and visual review are separate quality gates. A deck can compile correctly and still be a poor presentation.

## Repository discipline

- Keep slide-specific files under `Slides/`.
- Keep reusable presentation setup in `Slides/course.typ` and content in `Slides/slide_deck.typ`.
- Prefer small, local changes over speculative restructuring.
- If the same nontrivial layout or visual helper is copied more than once, consider moving it to `course.typ`.
- Do not move a one-off lecture-specific construction into `course.typ` merely to make the deck source look abstract.
- When changing the shared template, inspect representative slides afterward because a small theme change can affect the entire deck.

## Guiding principle

The slide source should read like the argument of the lecture. The shared template should make that argument easier to write, not become a second project that must be maintained.
